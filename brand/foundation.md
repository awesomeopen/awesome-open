# Foundation

## Purpose and scope

Awesome Open* catalogs software whose names begin with Open, including documented
expanded names. The prefix is a selection rule; it is not evidence of licensing,
quality, popularity or production readiness. `CONTRIBUTING.md` governs inclusion.
Older descriptions claiming an exclusively vetted, maintained open-source list
must not override that policy.

The field guide helps readers inspect a project's function, official sources and
available evidence. Working audience definition: people comparing software and
following those sources, especially developers and self-hosters. This is a
product framing inferred from the interface, not a completed audience study.

## Name and metaphor

- Brand spelling: **Awesome Open***, with the attached asterisk. In Markdown,
  escape the asterisk when necessary to preserve it as a literal character.
- **Genus Open*** is the field-guide framing, not a replacement project name.
- **Retro-Scraperism** names the interface/graphic language.
- **Speculative FOSSoligy** names the drawing language; retain that spelling.
- The specimen concept is fixed. Software records can be inspected like
  specimens. The artwork may suggest a function; it must not invent scientific
  classifications, motives, ancestry or diagnostic certainty.

## Voice

Use neutral, terse, matter-of-fact language. Put the result or action first. Use
ordinary labels for controls and evidence. Keep the visual strangeness in artwork
and organization; do not turn it into elaborate prose, personal interpretation,
fake archival secrecy or closing taglines. The detailed writing contract is in
[Retro-Scraperism](../site/RETRO-SCRAPERISM.md#writing-style-and-voice).

Examples: “Detected license”, “Last repository push”, “Reviewed alternatives”,
“Official source (GitHub)”. Avoid “license sincerity”, “active metabolism”, and
“forks of war” as unsupported classifications. A missing value stays unknown.

## Evidence contract

| Observation | Meaning that must be preserved |
| --- | --- |
| GitHub license detection | Metadata; not independent legal review |
| Stars / category top three | Count/ranking within that category; not endorsement |
| HN submissions / 2y | Matched submissions; not sentiment, adoption or controversy |
| Monthly stars retained at fetch | Retained stars in the cached history; preserve qualifications |
| Last push / repository creation | Repository timestamps; not project health/birth |
| Alternatives | Reviewed use-case comparison; not descent or feature parity |
| Registry ID | Stable canonical-URL identity; not display position |
| Folio number | Alphabetical position in the generated edition; not identity |

Release, Scorecard, function-summary and deployment evidence retain their own
source and review contracts. A design change must not erase uncertainty or
retrieval provenance to make a card cleaner.
