# Retro-Scraperism

Create a lucid instrument interrupted by strange life and a visible editorial hand. The interface must remain useful when artwork and metaphor are removed.

## Read the right source

For Awesome Open, read the current repository's `site/RETRO-SCRAPERISM.md`, `site/design/tokens.css`, and applicable repository instructions before editing. That project guide is canonical; do not silently replace it with this skill's snapshot. If repository access is unavailable, use `references/style-guide.md` and state that it is the v0.1 proposal snapshot, not a verified current project version. For other projects, use the snapshot as portable guidance and adapt factual labels to their domain.

Honor the user's explicit decisions and task scope. A style request does not authorize a full redesign, replacement of logos, extra website sections, publication, or a production merge. In Awesome Open, use the agreed branch/PR/private-preview workflow described by `site/PREVIEW.md` when working on design changes.

## Fix the concept before styling

For Awesome Open, **specimen** is deliberately selected. Do not reroll Journey, Stage, Cabinet or another concept because an upstream skill uses randomization. Elsewhere, adopt specimen only if the user's task fits inspectable records; ask or adapt when it does not.

Define the three layers in one short design note:

- Instrument: grid, typography, evidence and predictable controls.
- Specimen: one clear silhouette with one coherent impossibility.
- Editorial hand: a sparse, meaningful mark or marginal note.

Explain how the requested component serves its primary task. Avoid a new moodboard ceremony for a small edit.

## Apply the visual contract

- Paper is `#FFFFFF`; secondary paper is cool `#F0F5F8`. No sand, ivory, parchment, kraft, sepia, beige, leather or yellowed notebook substrate.
- Use ink `#111820`, Prussian `#0B2546`, and inverse trace `#D9EEF8` for structure. Readable accents on white: scarlet `#B62420`, emerald `#006B4F`. Amber `#FFC800` is a small highlight with ink text or focus on dark surfaces.
- Vivid red `#D9251D`, emerald `#00A86B`, and verdigris `#4A7C72` are artwork colors, not assumed accessible small-text colors. Check actual foreground/background pairs.
- Use two functional type voices. In Awesome Open, retain bundled Outfit plus system monospace; retain existing font provenance/licenses. An editorial serif is optional only when the content needs it. Handwriting never carries the only functional label.
- Use crisp rules, square edges, a 4px spacing base, restrained hard shadows and strong heading hierarchy. Keep dense evidence legible and comparable. Do not force a catalog into bento cards or fill it with theatrical whitespace.
- Keep primary controls plain, labeled and keyboard accessible. No wax-seal buttons, faux confidentiality, random VOID stamps or distressed warning text.
- Use sparse editorial marks only where they refer to something real. Never cover controls, sources or focus outlines.

## Direct original artwork

Use Speculative FOSSoligy when available for illustration, and read that skill before generating. Choose ink/pencil, selective crosshatching, convincing attachments and a coherent impossible principle. The subject should read immediately and become stranger on a second look. Vary silhouettes and functional analogies across a series. Biology does not need machinery; do not default to brass gears, cybernetic beetles or bio-steampunk.

Explicitly override warm-paper defaults with white, cold mist, blueprint or transparent grounds. Preserve established logos/favicon and source geometry unless replacement/transformation is requested. Do not republish the user's watermarked reference as a site asset without suitable rights/provenance. Use newly generated or authorized artwork when an actual component needs it; do not generate images just to satisfy a skill checklist.

If the frontend-image skill is invoked for section reference images, generate one separate horizontal image per requested section. Never turn a bounded style-guide task into unsolicited images for an entire website. Keep live UI text in HTML rather than baked into illustrations.

## Resolve other design-skill defaults

Use GPT Taste for hierarchy and refinement, the frontend-image skill for composition and image direction, and FOSSoligy for drawing logic. This explicit system overrides random theme/font choices, warm paper, mandatory GSAP pinning/scrubbing, forced AIDA/bento and obligatory mechanisms. Do not edit those other skills to manufacture an exception.

Motion must clarify state and support reduced motion. No scroll traps or initially hidden content that fails without JavaScript. Reading, search, evidence and source navigation take priority over spectacle.

## Writing style and voice

Apply these rules to all writing: interface copy, headings, annotations, documentation, reports, PR descriptions, and assistant responses.

- **Voice and tone:** Be neutral, terse, and matter-of-fact. Speak like a pragmatic senior colleague. Use the professional register of a staff engineer or technical editor: an unadorned report style. Avoid unsolicited empathy, pastoral warmth, inspirational framing, therapy speak, pseudo-profound framing, and rhetorical elevation.
- **Zero interpretation:** Do not analyze, reflect on, or comment on the user's mindset, emotions, motives, or underlying journey. Answer only the explicit operational premise. State relevant facts, actions, constraints, and uncertainties.
- **Answer first:** Put the concrete answer, result, or required action in sentence one. Never begin with a rhetorical wind-up or warm-up phrase such as “It makes sense that…”, “At its core…”, or “This speaks to a larger truth…”.
- **No editorial taglines:** Omit closing encouragement, philosophical takeaways, life advice, closing remarks, and unsolicited summaries. Stop when the requested information is complete.
- **Direct structure:** Omit filler transitions. Use precise verbs and literal headings. Include explanation only when it supports the requested operational answer; do not turn a technical observation into a broader life lesson.

The specimen concept governs visual organization and artwork; it does not authorize elevated prose or commentary about the reader.

| Avoid | Use |
| --- | --- |
| “It makes sense that you want clarity here.” | “The license is unknown.” |
| “At its core, this is a journey toward transparency.” | “Each record links to its sources.” |
| “You're building something meaningful. Keep going.” | Omit the closing remark. |

## Protect meaning

Use the specimen metaphor in art and editorial framing, not as invented data. In Awesome Open: unknown license is unknown; last push is a timestamp, not a maintenance verdict; repository creation is not project birth; alternatives are not ancestry; HN counts are not sentiment. Keep literal searchable labels and traceable sources. Do not turn missing information into red danger stamps.

## Finish at the requested scope

Check contrast, focus, keyboard behavior, narrow-screen reading, reduced motion, real asset paths and offline requirements as applicable. Report visual verification limits accurately. For a guide, distinguish proposed choices from user-approved direction. For system changes, update tokens/examples and the decision log together; keep this portable reference aligned when approved changes should travel between projects.

Before delivery, reject these drift signals: beige substrate, four competing type voices, decorative mechanics everywhere, fake secrecy, illegible distressed data, repeated insect silhouettes, and automatic scroll spectacle. Explain meaningful departures from the notes candidly, without claiming every detail in the supplied moodboard is mandatory.
