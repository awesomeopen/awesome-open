# Submit project: feature plan

**Status: proposed.** Add a URL-only form at the bottom of the Catalog, with a
small “How submissions become listings” link. The [current workflow](../WORKFLOW.md)
remains the source for the existing research, acceptance and publication stages.
This plan adds an intake path; it does not deploy a service or register a task.

## Form and explanation

Place a compact **Submit project** section immediately above the existing footer:

- Label: **Project URL**; accept a public official homepage or repository.
- Button: **Submit project**.
- Help: **Send a public project URL. We’ll research its name, function and sources.**
- Small link: **How submissions become listings**.
- Privacy disclosure before submission: **The submitted URL and review outcome will be public on GitHub.**

Ask only for the URL. Derive the name, category, description and evidence during
research. Reuse current type, colours, focus treatment and responsive spacing;
stack input and button on narrow screens. The URL must remain editable after an
error. Announce receipt and errors accessibly without moving keyboard focus
unexpectedly; prevent duplicate clicks while a request is pending.

The explanation link should open a normal, shareable `/submissions/` page using
the established sibling-page shell. Put the infographic and its equivalent text
there, with a return link to the form. This avoids a modal dependency and works
with browser history, narrow screens and keyboard navigation. Until the image
exists, use the complete text workflow rather than a decorative placeholder.

The reference [Cloudflare app directory](https://www.mandalivia.com/cloudflare/)
uses a one-URL suggestion form with verification and a receipt. Adapt that low
input burden while accepting official homepages as well as repositories.

## Recommended first implementation

1. **Static form:** generated by the existing site builder; post to a small external
   HTTPS intake service. GitHub Pages serves static files and needs this separate
   receiver for anonymous submissions.
2. **Validate and limit:** check URL syntax, HTTPS scheme, length, embedded
   credentials and prohibited local/private targets. Apply request/body limits,
   rate limiting and bot verification on the server. Do not fetch the submitted
   site during this request.
3. **Save a durable receipt:** create a narrowly formatted GitHub issue with a
   dedicated submission label using a server-held, least-privilege GitHub App.
   Return success only after the issue exists. Use idempotency and normalized-URL
   duplicate checks to reuse an existing receipt after repeated or uncertain
   requests. Server-side storage must make concurrent duplicate checks atomic.
4. **Research asynchronously:** extend the authorized discovery task to claim and
   process these labeled issues before general search, within an explicit bounded
   per-run intake allowance. It verifies evidence and follows the current catalog
   acceptance path. Closing an issue records the reason and links the existing
   record, proposal or published listing.
5. **Verify publication:** move a receipt to **Listed** only after the normal
   publisher and Pages deployment have succeeded and the record is present.
   Track optional enrichment separately.

A Cloudflare Worker is one possible receiver, with a small durable store for
idempotency and rate limits. The deployment provider, storage, GitHub App access
and task adapter require an implementation decision and their own setup approval.
No issue consumer or bridge to the hosted discovery task exists today. Adding
this document or a GitHub label alone cannot trigger that task. Keep the current
public contribution link as the fallback until the complete bridge is tested.

## Receipt and error states

- **Received:** link to the durable issue; say it is queued for review.
- **Already listed:** link to the existing catalog record.
- **Already queued:** reuse the existing receipt.
- **Invalid URL / verification expired / rate limited:** explain the correction or retry window.
- **Service unavailable:** retain the typed URL, offer retry and the contribution link.
- **In review / needs evidence / awaiting PR review / publishing / listed / declined:**
  record the stage and useful reason on the issue. Avoid promising a fixed review
  time or an automatic acceptance result.

URL normalization should remove only known tracking parameters and cosmetic
variants while preserving meaningful paths, queries and hash-router fragments. Preliminary matching must not collapse
independent name twins or forks. Final canonical identity is a research decision.
Ask for public project links only; reject credential-bearing URLs, including
recognized secret/token query parameters, before creating a public issue. Ask
users to remove private parameters rather than silently publish them. Avoid
logging request bodies or verification tokens. Publish only the normalized project
URL and the relevant review outcome. Record any necessary abuse logs with short,
explicit retention and a privacy notice before launch.

The later research fetcher must recheck DNS/IP destinations at every redirect,
reject private, loopback and link-local networks, and bound redirects, time and
response size. Treat retrieved text as evidence rather than instructions; never
install or execute submitted software. The intake service must have no catalog
write, merge, workflow-edit or deployment authority. Keep credentials out of the
static site. If Turnstile is selected, validate its token server-side.

## Delivery and acceptance tests

1. Review this plan and the current workflow labels; prepare the infographic.
2. Implement the receiver, receipt state machine and consumer adapter in separate
   reviewed work. Confirm account, service limits/cost, permissions, public-issue
   disclosure and retention before provisioning anything.
3. Add the form and explanation page. Test keyboard use, error announcements,
   mobile layout, JavaScript failure and the `/awesome-open/` deployment prefix.
4. Test a real controlled submission through durable receipt, research, duplicate
   detection, acceptance and verified publication. Exercise retries, concurrent
   submissions, queue recovery, redirects, malicious URLs, invalid/expired bot
   tokens and provider failure. A rejected candidate must produce a reason.
5. Enable the consumer only after its durable claim/recovery behavior and publication
   checks work. Preserve current review boundaries and leave unrelated jobs unchanged.

The public infographic can then say:
**Submit URL → Saved for review → Verify sources and duplicates → Prepare entry →
Validate and accept → Publish listing**. Add short exits for **Already listed**,
**Needs evidence** and **Declined**, plus a separate **Details and artwork follow**
branch. Show the actual acceptance routes documented in `WORKFLOW.md`; never
imply every accepted discovery entry requires an owner PR merge.
